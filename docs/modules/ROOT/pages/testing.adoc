= Testing Antora sites

This project provides utilities and guidelines for testing Antora documentation sites.

Quarkiverse projects usually host their Antora documentation in a dedicated `docs` Maven module.
After adding the `quarkus-antora` dependency, you can not only
xref:index.adoc#dev-mode[life-edit the site in Quarkus dev mode] but also

* Test that Antora is able to generate the site from your AsciiDoc sources
* Ensure that all external links are valid.

== Basic `@QuarkusTest`

The way we test the site generation is not much different from
https://quarkus.io/guides/getting-started-testing[testing any other Quarkus application].

First, you need to add the necessary dependencies

[source,xml,subs=attributes+]
----
include::example$testing/pom.xml[tag=basic-test]
----

Then you can add a basic `@QuarkusTest` as follows:

[source,java]
----
include::example$testing/AntoraSiteTest.java[tag=getIndex]
    ...
}
----

====

https://github.com/quarkiverse/quarkus-antora/tree/main/docs[`docs` module] of Quarkus Antora
====

== Detect dead links with `AntorAssured`

Antora takes care for validating internal cross-references but it does not help much with ensuring
that external links point to existing resources.
Page fragments (the part starting with `#` in `page.html#anchor`) are not validated by Antora too.

That's where the `io.quarkiverse.antorassured.AntorAssured` class provided by Quarkus Antora may come in handy.

[[persistent-cache]]
=== Persistent cache of remote pages

Link validation typically runs with every build, while most remote pages change rarely.
Some remote servers do not tolerate being accessed that often and respond with `429 Too Many Requests`.

Therefore, since Quarkus Antora 4.0.0, `AntorAssured` stores the remote pages it has fetched in the local file system
and reuses them in subsequent runs.
The cache is enabled by default.

[cols="1,2"]
|===
|Setting |Default

|Cache directory
|`~/.cache/antorassured/pages`, where `~` is the value of the `user.home` system property

|Expiration: pages fetched longer ago are fetched again
|36 hours

|Garbage collection age: pages fetched longer ago are deleted from the cache directory
|180 days
|===

The cache works as follows:

* Before a page is fetched, the cache directory is consulted.
  If the page was stored there within the expiration period, it is not requested from the remote server.
  The stored page is used instead, also for validating the fragments of the links.
* A cached page does not count against any `RateLimit` and it is never delayed by it.
  It is still counted by policies such as `AggregatePolicy.countAtLeast(200, n)`.
* Only responses having a `2xx` status are stored.
  Other responses, such as `404`, `429` or `503`, timeouts and connection failures are never stored,
  so broken links are checked against the remote server with each run.
* The site under test is never stored.
  By default, this applies to all URIs whose host is `localhost` or a loopback IP address, such as `127.0.0.1`.
  `LinkStream.validate()` (without parameters) in addition excludes all URIs under the base URI of the site under test,
  which is important if you set `quarkus.http.test-host` to some other host name.
* URIs containing credentials, such as `+https://user:password@example.com/+`, are never stored.
* Pages requested with different `Accept` headers are stored separately.
  Other request headers are not taken into account.
* The cache directory can be used by several builds at the same time.

==== Stale pages

The cache makes the validation faster and less demanding for the remote servers at the cost of working with pages
that may be up to 36 hours old (or whatever expiration you set):

* A link to a page that was removed from the remote server in the meantime is still reported as valid.
* A link to a fragment that was added to the remote page in the meantime is still reported as invalid.

Both issues go away after the cached page expires.
If you do not want to wait, delete the cache directory or only the directory of the given page.
The path of the directory is derived from the URI of the page as follows:
`<cache directory>/<reversed host name>/<scheme>/<port>/<accept header>/<path>`.
For example, `+https://quarkus.io/guides/building-native-image+` is stored in
`~/.cache/antorassured/pages/io/quarkus/https/443/no-accept/guides/building-native-image`.
Characters that are not allowed in file names on some operating system are replaced by underscores.

Deleting the files is always safe.
The validation never fails because of a missing or broken content of the cache directory.

==== Garbage collection

At the end of each validation that has used the cache, the pages fetched more than 180 days ago are deleted from the cache
directory, together with the directories that became empty.
These are typically pages that are not linked from your documentation anymore.
Files not created by `AntorAssured` are never deleted.

[[persistent-cache-ci]]
==== Using the cache on CI

The cache is useful on CI only if the cache directory is restored before the build and saved after it.
The directory to save and restore is `~/.cache/antorassured/pages`, unless you have configured another one.
It can be copied to another machine, even to one running a different operating system.

[NOTE]
====
The pages are stored as they were received, without any encryption.
Keep that in mind if you validate links to private resources, for example using `LinkGroup.bearerToken(String)` or
`LinkGroup.basicAuth(String, String)`, and you share the cache directory with others.
The tokens and passwords themselves are never stored.
====
